# Unified ASP.NET Core Identity domain in the original Gamefilled

**Status:** first real code integration slice, 2026-10-22. The
**original Gamefilled.csproj** now compiles the future consolidated
ASP.NET Core Identity domain, not another website.

## Integrated source / proposed future database

- `Identity/GamefilledAccount.cs` contains one `IdentityUser<Guid>`
  (email, profile, avatar, bio and visibility).
- `Identity/GamefilledDomain.cs` contains the account-owned game entries,
  featured favorites, follow graph, activity, notifications and **blocking**
  entities, all with GUID user ownership, not the old integer session user ID.
- `Data/GamefilledV2DbContext.cs` is one
  `IdentityDbContext<GamefilledAccount, IdentityRole<Guid>, Guid>`.
  Normalized emails have a unique database index. Game/library status,
  rating, reviews and follow pairs have database-level constraints,
  uniqueness, GUID foreign keys and ownership links.
- `tests/Gamefilled.Tests/UnifiedIdentityDomainTests.cs` checks the
  canonical model's EF metadata, uniqueness and foreign key types.
- `Application/Identity/GamefilledV2LibraryService.cs`,
  `GamefilledV2NotificationService.cs` and `GamefilledV2SocialService.cs`
  contain reusable claim-owned library, review, recipient-scoped notification,
  follow/unfollow and block/unblock operations. Private profiles cannot be
  followed without a future explicit consent mechanism.
- `tests/Gamefilled.Tests/UnifiedIdentityOwnershipTests.cs` provides
  isolated ownership, review persistence, block and redirect-safety tests.
  These are NOT equivalent to SQL migration tests or browser acceptance.
- `Data/GamefilledV2DbContextFactory.cs` allows *design-time* migration
  generation without defaulting to the real development DB.
- The existing legacy EF baseline/migration bundle explicitly uses
  `AppDbContext` so merely introducing this new context cannot
  unexpectedly migrate the running SQL database.

## SQL migration baseline — generated and integration-tested

- EF Core migration `Data/V2Migrations/20261022223030_InitialUnifiedIdentity.cs`,
  generated by the official `dotnet-ef migrations add` tooling; the matching
  `.Designer.cs` and `GamefilledV2DbContextModelSnapshot.cs` are committed
  beside it, separate from the historical `AppDbContext` baseline.
- Builds **13 tables**: seven standard Identity `AspNet*` tables and
  `GamefilledGameEntries`, `GamefilledFavoriteGames`,
  `GamefilledFollows`, `GamefilledActivities`,
  `GamefilledNotifications` and `GamefilledBlocks`.
- `.github/workflows/v2-unified-sql.yml` uses a disposable SQL Server 2022
  instance named `GamefilledV2IntegratedCI` to apply the migration,
  verify that no EF model changes are pending, apply it **a second time**
  to confirm idempotence, and run real SQL constraint/foreign-key tests.
  SQL tests deliberately submit duplicate library entries, invalid statuses,
  self-follows/self-blocks and nonexistent account IDs, and verify rejection.
- This is an independent test database: `GamefilledFullPreview`,
  `GamefilledV2Preview` and the dev `Gamefilleddb` are not touched.
  There is still **no automatic migration** in the live runtime and no
  V2 authentication cutover.
- The future private preview migration must be run via an explicit,
  reviewed, preview-only operation with backups and resource checks.
  Never run the new migration bundle against the old development database.

**This is schema/model source, NOT yet the active authentication system.**
The current `GamefilledFullPreview` runtime still uses legacy sessions,
and no GUID schema migration has been generated/applied or provisioned on
`docker-01`. Do not claim new auth security is active in the browser yet.


## Branded Razor form integration, staged safely

- `Application/Identity/PageModels/GamefilledIdentityLoginPageModel.cs`
  and `GamefilledIdentityRegisterPageModel.cs` preserve every input field
  expected by `Pages/users/Login.cshtml` and `Pages/users/Register.cshtml`.
- Email confirmation, resend, generic forgot-password and token-reset
  handlers are prepared in `Application/Identity/PageModels/`, but **not
  exposed as routes** until the complete coordinated cutover.
- Strong password policy is checked before telling the user that a
  registration was accepted, matching the official Identity validator.
- Existing Gamefilled auth page artwork, background, markup and CSS are
  unchanged. Contract tests assert this and fail if a generic UI replaces
  the originals or if authentication middleware is enabled prematurely.
- At cutover, update the `@model` references, registration pending/verified
  messages, final password help text and recovery pages **without** changing
  the visual theme. Keep login, library and profile handlers under one
  verified Identity principal; **do not enable one route early**.

## Required next implementation gates

1. Generate and code-review an `InitialUnifiedIdentity` EF migration
   **for `GamefilledV2DbContext` only** and apply it to a new, separate
   disposable SQL database `GamefilledV2Integrated` on the preview VM.
   Never migrate or overwrite `web-01` / `Gamefilleddb`.
2. Use one DbContext and the new principal for every authenticated page
   and handler. Adapt `/users/Login`, `/users/Register` and the existing
   visual form templates, integrate tested Resend verification, reset and
   account settings, and ensure Identity cookies/security stamps.
3. Replace every `Session.GetInt32/GetString("userId"/"username")` authority
   in profiles, library, reviews, follows, people, favorites, activity,
   notifications and settings. No compatibility login or dual-authority
   fallback in a live environment.
4. Test email verification, password reset, invalid/reused tokens, cookie
   revocation, CSRF, per-user ownership, concurrency, unique indexes,
   FKs, status constraints, and end-to-end browser parity.
5. Only switch the preview to the integrated SQL-backed app once all
   handlers pass; keep main layout, logo/backgrounds, UI, card CSS and
   IGDB query strategies unchanged.
6. Archive/remove legacy auth models/services/tables/code only *after*
   clean-suite tests show no live runtime dependencies. Never delete the
   preview data or live database to paper over an incomplete migration.
7. Off-host encrypted backup/restore rehearsal and explicit owner's
   acceptance are compulsory before deploying to the real site.
